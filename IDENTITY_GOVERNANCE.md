# Chronos Data Model Governance & Canonical Identity Definition (Draft)

**Version:** 0.1.0
**Date:** 2026-04-25
**Owner:** Skynet / Oliver
**Status:** Draft - Requires team review and final sign-off (Phase 3 Gate).
**Purpose:** This document establishes the immutable, single source of truth for all identity identifiers used within the FloLabs Chronos system. It governs the relationship between various IDs to ensure data integrity across all microservices (CRM, Notion, Authentication, etc.).

---

## 1. Canonical Identity Principle

The core principle of Chronos identity is that every individual (person) must be represented by a singular, immutable primary identifier. We are moving away from fragmented, system-specific IDs towards a unified, canonical model.

## 2. Defined Identifiers

The following identifiers are recognized within the system. Their scope and ownership must be strictly defined:

### A. User ID (The Canonical Identifier)
*   **What it is:** The primary, system-level identifier for any account holder (internal employee, administrative user, etc.) who has an active, authenticated profile within the Chronos ecosystem.
*   **Ownership:** `Chronos Core Service` (The central identity management service).
*   **Format:** UUID v4 (Example: `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`).
*   **Immutability:** Must never change throughout the lifecycle of the user record.
*   **Use Case:** Used for all internal application-to-application and module-to-module references.

### B. Applicant ID
*   **What it is:** The identifier assigned to an external candidate or prospect *before* they are fully onboarded, verified, and elevated to a system User.
*   **Ownership:** `ATS/CRM System` (The front-end talent tracking system).
*   **Format:** A UUID v4, but with a mandatory prefix or namespace UUID segment (e.g., `applicant-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`).
*   **Lifecycle:** This ID is temporary. It is the primary key for candidate records until activation.
*   **Transition Rule:** Upon successful onboarding and validation (Phase 3), the system **must** create a new `User ID` and link the `Applicant ID` to the `User ID` record (See Relationship Diagram).

### C. External System IDs (Non-Canonical)
*   **Examples:** Notion Database IDs (`a1a106fab63548089279dc54d63eab89`), AWS Resource ARNs, Google Workspace IDs, etc.
*   **Status:** These are **Foreign Keys (FK)** and are permissible for storing context but **must not** be used as a primary join key for core identity management.
*   **Mitigation:** All interactions with external systems must pass through a dedicated Integration Layer Service (ILS) that manages the ID mapping.

## 3. Identity Relationship Graph (The Linkage)

The relationship between IDs must flow linearly and is the primary focus of Phase 3 cleanup:

1.  **New Candidate:** `Applicant ID` is generated by the ATS/CRM.
2.  **Onboarding/Verification:** The system verifies the candidate/user details.
3.  **Identity Creation:**
    *   If external systems (e.g., Single Sign-On) provide a unique identifier, this may map to the new `User ID`.
    *   The system **commits** the `Applicant ID` $\rightarrow$ `User ID` mapping in the Identity Mapping table.
4.  **Active State:** From this point forward, the `User ID` is the golden record for the identity.

## 4. Data Governance Commitments

*   **Commitment 1 (Data Source):** The `Chronos Core Service` is the sole authority for generating and updating `User IDs`.
*   **Commitment 2 (APIs):** All APIs that reference an identity must accept and prioritize `User ID` as the primary input parameter, with `Applicant ID` usage being deprecated or requiring explicit `User ID` resolution.
*   **Commitment 3 (Documentation):** This document must be versioned and updated whenever a structural change to the ID schema occurs.
